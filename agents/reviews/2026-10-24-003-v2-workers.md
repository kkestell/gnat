## F1. Immediate direction can stall behind worker interruption

Medium · Concurrency · Fixed · `internal/v2/core/coordination.go:16`

When the orchestrator interrupts a worker and immediately sends further
instructions, the previous execution can still be shutting down. The message
was accepted while the worker's persisted lifecycle was still `running`.
Scheduling returned because that execution remained active, and its later
`interrupted` outcome did not schedule the accepted direction. The continuation
stayed queued until another explicit message or swarm resume happened.

### Evidence

A focused reproduction held the fake adapter's cancellation cleanup behind a
channel, interrupted the worker, sent ordinary direction during that interval,
and released cleanup. Before the fix, the check failed with
`accepted follow-up stranded: queued`. The existing continuation test waited
for the worker's `interrupted` lifecycle before sending and did not exercise
this interval.

### Fix

The parent presented the finding before authorizing changes under the invoked
autonomous workflow. `send_message` now waits for its target's stopping
execution to settle before accepting the direction, using the same locking
pattern as swarm resume. The existing prerequisite check and exact saved
session then handle continuation. Removal keeps its existing immediate message
rejection. This follows the plan's already agreed ordinary-message behavior;
no new product behavior or retry mechanism was introduced.

Added `TestWorkerDirectionWaitsForInterruptionToSettle`, covering the gated
cleanup interval, acknowledgment after cleanup, prompt delivery into the same
saved session, and request replay without duplicate input.
